LostRuins 재설계서

1편에서 진단한 문제를 실제 코드로 다시 설계했습니다. C++ 게임 서버와 Unity 클라이언트 코드를 직접 작성해 컴파일하고, 봇 3명을 붙여 지연·손실 환경에서 측정했습니다. 무엇이 가장 크게 바뀌는지, 클래스 구조가 어떻게 달라지는지, 전체 소스, 측정값, 그리고 8개월 안에 만들려면 어떤 순서였어야 했는지를 정리했습니다. 이 판은 현업 기준 재검증(3편 15장, 17건 수정)을 반영한 최종본입니다.

00이 문서를 읽는 법

1편이 "무엇이 왜 잘못됐나"였다면 2편은 "그럼 어떻게 만들었어야 하나"입니다. 이번에는 설계만 그리지 않고 프로토타입을 만들어 돌렸습니다. 다만 범위는 궁수 1직업, 박스로 단순화한 맵, 몬스터 12마리입니다. 원본 게임 전체를 옮긴 것이 아닙니다.

01가장 크게 바뀌는 것

  1. 규칙이 사는 곳

    데미지, 명중, 치명타 난수, 몬스터 AI, 체력, 쿨타임이 Unity 컴포넌트에서 서버의 순수 C++ 시뮬레이션(World)으로 옮겨 갑니다. 클라이언트에는 입력, 예측, 표현만 남습니다. 1편의 F1·F2·F3이 이 한 가지로 동시에 사라집니다.

  2. 이동 코드의 성격

    Rigidbody와 애니메이션 이벤트에 맡기던 이동이, C++과 C#에서 비트 단위로 같은 결과를 내야 하는 순수 함수 Step()이 됩니다. 서버가 판정하면서도 내 캐릭터가 즉시 반응하려면 이 방법밖에 없습니다. 담당하셨던 영역에서 가장 큰 변화이고, 가장 어려운 부분입니다.

  3. 클래스 구조

    상속 4단(MonoBehaviour → PlayerState → Dealer → MultiDealer)이 데이터(스킬 표)와 조합(예측기, 보간기, 뷰)으로 바뀝니다. 멀티 전용 클래스는 0개입니다. 싱글플레이도 같은 서버에 혼자 접속하는 것뿐입니다.

03전체 구조

실선은 이번 프로토타입에 구현한 부분, 점선은 실서비스에 필요하지만 설계만 한 부분입니다. 클라이언트와 게임 서버 사이에는 패킷 두 종류만 오갑니다. 클라이언트는 "무엇을 하고 싶은지(입력)"만 보내고, 서버는 "무슨 일이 일어났는지(상태와 이벤트)"만 보냅니다.

한 틱 안에서 일어나는 일 (33ms)

  1. 소켓에 쌓인 패킷을 모두 읽어 플레이어별 입력 큐에 넣는다 (중복 번호는 버림)
  2. 플레이어마다 입력 1개를 꺼낸다. 아직 안 왔으면 직전 입력을 반복한다
  3. 공유 Step()으로 이동한다. 클라이언트 예측과 같은 함수다
  4. 눌린 버튼과 쿨타임으로 스킬을 발동한다. 데미지 난수는 여기서만 굴린다
  5. 화살을 이동시키고 이번 틱 경로(선분)와 몬스터(구)를 검사한다 → HitEvent
  6. 몬스터 FSM: 대기 → 추적 → 준비 동작 → 공격 → 회복
  7. 클라이언트마다 스냅샷 1개를 만들고, 아직 ACK 안 된 이벤트를 다시 싣는다

스레드는 몇 개가 필요한가

프로토타입은 스레드 1개입니다. 측정한 틱 비용은 방 하나에 평균 약 90µs이고, 순수 시뮬레이션만은 몬스터 12마리에 1.5µs입니다. 이론상 스레드 하나로 방 수백 개를 돌릴 수 있습니다. 계산

그래서 학생 규모에서는 단일 스레드가 정답입니다. 실서비스로 키울 때는 소켓 I/O 스레드와 방 로직 스레드를 나누고, 그 사이는 잠금 없는 큐로 연결합니다. 방 하나는 항상 같은 스레드가 맡게 해서 방 안에서는 락이 필요 없게 합니다. 멀티스레드는 측정해서 필요해질 때 도입합니다.

05패킷은 두 종류면 충분합니다

1편의 원본은 RPC 이름 문자열과 인자 배열을 기능마다 따로 보냈습니다. 재설계에서는 입력 패킷과 스냅샷 패킷이 전부입니다. 아래 막대는 비트 배치이고, 길이는 비트 수에 비례합니다.

입력 패킷에는 최근 입력 4개를 함께 싣습니다. 패킷 3개가 연속으로 사라져도 네 번째가 메워 줍니다. 이벤트(명중, 사망)는 ACK가 올 때까지 매 스냅샷에 다시 실립니다. 재전송 타이머가 없으므로 TCP처럼 앞 패킷을 기다리며 멈추지 않습니다. 측정에서 평균 입력 패킷은 37.9바이트, 스냅샷은 230~246바이트였습니다. 스냅샷은 1,200바이트를 넘지 않도록 먼 엔티티부터 뺍니다(몬스터 200마리에서 최대 1,200바이트 실측). 실측

06지연을 숨기는 방법

서버가 판정하면 입력이 서버까지 갔다 와야 결과가 나옵니다. 그 시간 동안 내 캐릭터가 멈춰 있으면 1편의 0.45초 점프보다 나빠집니다. 그래서 클라이언트는 같은 Step()으로 먼저 움직이고(예측), 서버 결과가 오면 비교해서 다르면 되감아 다시 계산합니다(재조정). 다른 플레이어와 몬스터는 약간 과거를 보간해서 그립니다.

시나리오 (20초, 봇 3명, 입력 버퍼 1틱)예측 비교비트 일치보정최대 보정서버 확인 p50 / p95근거

보정은 왜 생기나

보정은 전부 입력이 서버 틱보다 늦게 도착해 서버가 직전 입력을 반복한 경우에 생깁니다. 그래서 재검증에서 서버가 입력을 1틱 모아 두고 시작하는 입력 지터 버퍼를 넣었습니다.

07클래스 다이어그램

1편의 상속 트리와 비교해 보세요. 서버는 데이터를 담는 구조체 몇 개와 그걸 돌리는 World가 전부이고, 클라이언트는 상속 없이 조합으로 되어 있습니다. 화살표는 "가지고 있다", 점선은 "같은 공유 코드를 쓴다"입니다.

101편의 항목은 이렇게 해결됩니다

  

    
1편재설계의 해결결과근거

    
      
F1 매 프레임 RPCRPC 없음. 클라는 30Hz 입력 1개, 서버는 30Hz 스냅샷 1개룸 패킷 초당 180개, 행동과 무관하게 일정실측

      
F2 TCPUDP + ACK 비트필드, 이벤트는 ACK까지 재적재손실 5%·왕복 200ms에서 확인 지연 p95 342ms (왕복 + 버퍼 + 틱 수준), 멈춤 없음실측

      
F3 판정 분열명중·데미지·치명타 난수 모두 서버 World지연 0에서 서버 명중 49건 = 쏜 사람이 받은 명중 이벤트 49건실측
