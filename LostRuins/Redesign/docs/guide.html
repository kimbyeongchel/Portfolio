00이렇게 읽으세요

모든 개념 카드는 같은 순서로 되어 있습니다. 한 줄 뜻 → 일상 비유 → 직접 만져 보는 그림 → 게임에서는 → 코드에서는 → 왜 이 방법인가(다른 방법과 비교). 처음에는 비유와 그림만 보고 넘어가도 됩니다. 두 번째 읽을 때 코드와 비교 표를 보세요.

순서는 2장 "화살 한 발의 여행"을 먼저 보는 것을 추천합니다. 서버가 하는 일 전체를 한 번에 따라가 볼 수 있고, 뒤의 개념들은 그 여행의 한 구간을 확대한 것입니다.

숫자는 2편과 같은 기준입니다. 실측은 이 분석 환경에서 프로토타입을 실행해 잰 값이고, 시뮬레이션은 이 페이지 안의 그림이 계산한 값입니다. 실제 인터넷과 Unity에서 잰 값은 아닙니다.

02화살 한 발의 여행

마우스를 한 번 눌러 화살을 쏘면, 그 입력은 내 컴퓨터를 떠나 서버에서 판정을 받고 세 명의 화면으로 돌아옵니다. 단계마다 어떤 코드가 일을 하는지 따라가 보세요. 번호를 누르거나 자동 재생을 켜면 됩니다.

전체 왕복은 "왕복 시간 + 서버 틱을 기다리는 최대 33ms + 클라 틱을 기다리는 최대 33ms"입니다. 2편의 측정에서 왕복 100ms일 때 입력부터 서버 확인까지 p50 153ms가 나온 이유입니다. 그 사이에도 내 캐릭터는 6단계 "예측" 덕분에 이미 움직이고 있습니다.

03 · 전송 방식 · 1편 F2

TCP와 UDP

TCP는 모든 데이터를 순서대로 빠짐없이 전달하고, UDP는 보내기만 하고 도착을 보장하지 않습니다. 게임의 위치 정보처럼 "최신 값만 중요한" 데이터에는 UDP가 맞습니다.

TCP는 계산대가 하나뿐인 마트입니다. 맨 앞 손님의 카드가 결제 오류가 나면, 뒤의 손님들은 계산이 끝났어도 그 사람이 해결될 때까지 모두 기다립니다. UDP는 전광판입니다. 지난 숫자 하나가 안 보였어도 다음 숫자가 뜨면 그만입니다. 축구 스코어 전광판에서 2:1을 못 봤어도 지금 3:1이 보이면 문제없습니다.

게임에서는

1편의 원본은 Photon 설정이 TCP였습니다. 무선 연결처럼 손실이 있는 한 명의 패킷 하나가 사라지면, 그 뒤의 위치·스킬 정보가 모두 줄을 서서 기다렸습니다. "그 사람만 2~3초 늦던" 현상과 맞아떨어집니다.

코드에서는

udp_socket.h가 UDP 소켓을 열고, 꼭 도착해야 하는 이벤트(명중, 사망)만 reliability.h가 "확인 올 때까지 계속 다시 싣는" 방식으로 챙깁니다. 위치는 매 틱 새로 보내므로 하나쯤 잃어도 다음 것이 덮어씁니다.

왜 이 방법인가

방법장점단점판단
TCP구현이 가장 쉬움, 순서·도착 보장손실 하나가 뒤 데이터 전부를 멈춤실시간 위치에는 부적합
UDP + 직접 만든 ACK멈춤 없음, 필요한 것만 신뢰 전송, 구조를 배우기 좋음신뢰성 코드를 직접 짜야 함 (약 120줄)이번 선택: 학습 + 포트폴리오 가치
ENet · GameNetworkingSockets · KCP검증된 신뢰 UDP 라이브러리내부 동작을 이해 못 하면 디버깅이 어려움실서비스라면 이쪽을 추천

위치처럼 계속 바뀌는 값은 잃어도 되게 UDP로, 명중처럼 꼭 도착해야 하는 사건만 확인될 때까지 다시 보낸다.

04 · 판정 권한 · 1편 F3

누가 "맞았다"를 정하나

판정 권한은 "결과를 결정하는 컴퓨터가 어디인가"입니다. 여러 곳이 각자 정하면 결과가 어긋나고, 한 곳이 정하고 나머지는 따르면 모두가 같은 결과를 봅니다.

심판 없는 축구를 생각해 보세요. 공격수는 "골!", 수비수는 "오프사이드!", 관중은 "노골!"이라고 각자 판정하면 경기가 성립하지 않습니다. 그래서 심판 한 명이 판정하고, 선수와 관중은 그 판정을 전광판으로 받아 봅니다. 서버가 그 심판입니다.

게임에서는

"내 화면에서는 맞았는데 데미지가 안 들어감", "이펙트가 사람마다 다른 곳에 뜸"이 이 문제였습니다. 전사는 공격한 본인이, 궁수는 마스터 화면이 판정하는 식으로 직업마다 심판이 달랐던 것도 원인입니다.

코드에서는

클라이언트가 보내는 건 InputCmd(방향, 버튼)뿐입니다. 화살 생성(World::Fire), 데미지 난수(RollDamage), 명중(StepProjectiles)은 모두 서버의 world.cpp에만 있습니다. 클라이언트의 CombatPresenter는 서버가 보낸 HitEvent를 받아 그리기만 합니다.

왜 이 방법인가

방법장점단점판단
각 클라가 판정 (원본)반응이 빠름, 서버 불필요결과가 어긋남, 조작에 무방비협동 게임에서도 문제가 생김
호스트 1명이 판정서버 비용 없음, 판정은 한 곳호스트가 나가면 끝, 호스트 회선이 모두에게 영향협동 게임의 현실적 정답
전용 서버가 판정공정, 조작 방지, 호스트 의존 없음서버를 만들고 운영해야 함이번 선택: C++ 서버를 배우는 목적

클라이언트는 의도만 보내고, 결과는 서버 한 곳이 정해서 모두에게 같은 내용으로 알려 준다.

05 · 서버의 심장 박동

고정 틱

틱은 서버가 세상을 한 걸음 진행시키는 단위입니다. 이 서버는 1초에 30번, 33ms마다 정확히 한 번씩 "입력 처리 → 이동 → 판정 → 결과 전송"을 합니다.

메트로놈입니다. 박자가 일정해야 여러 연주자가 맞출 수 있듯이, 서버와 클라이언트가 같은 박자(33ms)로 걸음을 세야 "입력 #1201번은 몇 번째 걸음에 처리됐다"를 서로 맞춰 볼 수 있습니다. 렌더링은 60~144fps로 들쭉날쭉해도 게임 규칙의 박자는 고정입니다.

게임에서는

원본의 PlayerState.Update는 렌더 프레임마다 돌았습니다. 60fps 컴퓨터와 144fps 컴퓨터에서 매 프레임 일어나는 일이 달랐고, 그래서 마우스 감도나 RPC 횟수가 fps에 따라 변했습니다(1편 F1, F5).

코드에서는

GameServer::Run이 "다음 틱 목표 시각"을 33,333µs씩 누적합니다. 한 틱이 늦어도 다음 틱이 따라잡아 평균 30Hz가 유지됩니다. 클라이언트는 GameClient.Update의 누산기(accumulator)로 같은 박자를 셉니다.

왜 30Hz인가

틱 속도장점단점판단
10~20Hz대역폭·CPU 절약입력 반응이 거칠어짐 (50~100ms 단위)MMO, 전략 게임
30Hz액션 협동에 충분, 대역폭 적당 (클라당 약 8KB/s 실측)정밀 격투·슈팅에는 부족이번 선택
60~128Hz정밀한 판정대역폭·CPU 2~4배FPS, 격투 게임

서버는 33ms 박자에 맞춰 세상을 한 걸음씩 진행하고, 클라이언트도 같은 박자로 세기 때문에 서로의 걸음을 비교할 수 있다.

06 · 지연 숨기기 ① · 2편 6장

클라이언트 예측과 재조정

서버가 판정하면 결과가 왕복 시간만큼 늦게 옵니다. 그래서 내 캐릭터는 서버를 기다리지 않고 같은 규칙으로 먼저 움직이고(예측), 결과가 오면 비교해서 다르면 되감아 다시 계산합니다(재조정).

터널 속 내비게이션입니다. GPS 신호가 끊겨도 화면 속 차는 지금 속도와 방향으로 계속 움직입니다(예측). 터널을 나와 신호가 잡히면 실제 위치와 비교해서, 다르면 그 지점부터 다시 계산합니다(재조정). 대부분은 예측이 맞으므로 아무 일도 일어나지 않습니다.

게임에서는

1편의 원본은 내 스킬도 서버를 돌아와야 실행되는 구조(AllViaServer)여서 입력 반응이 왕복 시간만큼 늦었습니다. 재설계에서는 이동과 점프가 0틱 만에 반응하고, 2편 측정에서 지연 0일 때 1,791번 비교가 전부 일치했습니다.

코드에서는

LocalPlayerPredictor.Predict가 입력마다 Movement.Step을 돌리고 결과를 번호별로 기록합니다. Reconcile은 서버가 "입력 #N까지 반영한 상태"를 보내면 내 기록 #N과 비트 단위로 비교하고, 다르면 서버 상태에서 #N+1부터 다시 계산합니다.

왜 이 방법인가

방법장점단점판단
서버 결과를 기다림항상 정확모든 입력이 왕복 시간만큼 늦음턴제·전략 게임
클라가 판정하고 서버는 믿음즉시 반응조작·불일치 (원본의 문제)부적합
예측 + 재조정즉시 반응하면서 서버가 판정이동 규칙이 C++·C#에서 비트까지 같아야 함 (11장)이번 선택, 액션 게임 표준

내 캐릭터는 같은 규칙으로 먼저 움직이고, 서버가 확인해 준 결과와 다르면 그 시점부터 다시 계산한다.

07 · 지연 숨기기 ② · 1편 F6

다른 사람은 100ms 과거를 그린다

다른 플레이어와 몬스터의 위치는 33ms마다, 그것도 들쭉날쭉하게 도착합니다. 받은 즉시 그리면 뚝뚝 끊기므로, 일부러 100ms 늦게, 앞뒤 두 스냅샷 사이를 이어서 그립니다.

동영상 스트리밍의 버퍼입니다. 영상 앱은 몇 초를 미리 받아 두고 조금 늦게 재생합니다. 그래서 와이파이가 잠깐 흔들려도 영상이 멈추지 않습니다. 여기서는 몇 초가 아니라 0.1초만 늦게 그려서, 늦어진 만큼 움직임을 정확하고 매끄럽게 보여 줍니다.

코드에서는

SnapshotInterpolator.Add가 스냅샷을 서버 틱 번호와 함께 저장하고, Sample이 "지금 서버 틱 − 3틱" 시점을 찾아 앞뒤 스냅샷 사이를 비율 u로 섞습니다. 각도는 350°→10°를 −340°가 아니라 +20°로 짧게 돌도록 처리합니다.

내 캐릭터는 왜 다르게 하나

내 캐릭터에 100ms 지연을 주면 조작감이 망가집니다. 그래서 내 캐릭터는 6장의 예측, 남은 모두는 보간입니다. 화면 속 시간이 둘로 나뉘는 셈이고, 현업 액션 게임 대부분이 이 구조입니다.

다른 사람은 0.1초 늦게, 대신 받은 스냅샷 사이를 정확히 이어서 그린다.

08 · 재검증에서 추가 · 수정 이유

입력 지터 버퍼

서버는 틱마다 각 플레이어의 입력을 하나씩 꺼내 씁니다. 입력이 조금 늦게 도착해 큐가 비어 있으면 직전 입력을 반복하고, 그게 클라이언트 보정의 원인이 됩니다. 그래서 입력 하나를 미리 쌓아 두고 시작합니다.

회전초밥 레일입니다. 주방이 접시를 정확히 손님이 집는 박자에 맞춰 올리면, 주방이 1초만 늦어도 손님 앞이 빕니다. 레일에 접시 하나를 미리 올려 두면 주방이 조금 늦어도 손님은 계속 먹을 수 있습니다. 대신 손님이 먹는 접시는 항상 한 접시만큼 먼저 만든 것입니다(33ms 늦음).

프로토타입 실측 (봇 3명, 20초)버퍼 0버퍼 1틱근거

왜 1틱인가

버퍼장점단점판단
0확인 지연 최소지터가 있으면 반복 → 보정재검증 전 상태
1틱 (33ms)왕복 100ms·손실 2%에서 보정 0회서버 확인이 1틱 늦어짐 (내 화면 반응은 예측이라 그대로)이번 선택
2틱 이상 / 적응형나쁜 회선에서도 안정지연 증가. 적응형은 구현 복잡현업 대형 게임은 회선 상태에 따라 자동 조절

입력을 한 개 미리 쌓아 두면 33ms를 내주는 대신 네트워크 흔들림 때문에 생기던 보정이 사라진다.

09 · 패킷 다이어트

비트 직렬화와 양자화

직렬화는 메모리 속 데이터를 한 줄의 바이트로 펴는 일, 양자화는 실수를 "몇 번째 눈금인가"라는 정수로 바꿔 줄이는 일입니다.

자의 눈금입니다. "10.1234567m"를 그대로 적는 대신 "1cm 눈금으로 1012번째"라고 적으면 훨씬 짧습니다. 눈금이 촘촘할수록 정확하지만 숫자가 길어집니다. 화면에 그릴 위치는 1cm 정도 오차면 아무도 모릅니다.

예외: 내 캐릭터는 양자화하지 않음

재조정은 "내 기록과 서버 결과가 비트까지 같은가"를 봅니다. 양자화하면 0.78cm 단위로 뭉개져 항상 달라 보이므로, 내 캐릭터의 상태만은 float 원본(32비트 × 6)을 보냅니다.

코드에서는

BitWriter::WriteQuantized가 값을 0~1로 정규화하고 눈금 수를 곱해 반올림합니다. 재검증에서 반올림을 "0.5 더하고 버림"에서 std::lround로 바꿨습니다. 0.49999997처럼 경계에 걸린 값은 0.5를 더하는 순간 float 반올림으로 1이 되어 한 칸 틀릴 수 있기 때문입니다.

화면에 그릴 값은 눈금 번호로 줄여 보내고, 판정 비교에 쓰는 값만 원본 그대로 보낸다.

10 · UDP 위의 신뢰성

ACK 출석부와 등기우편

UDP는 도착을 알려 주지 않으므로, 패킷마다 "내가 최근에 받은 33개가 무엇인지"를 함께 실어 보냅니다. 꼭 도착해야 하는 이벤트는 그 출석부에 체크될 때까지 계속 다시 싣습니다.

출석부입니다. 선생님(받는 쪽)이 매 시간 "오늘 33명 중 누가 왔는지" 한 줄로 적어 돌려줍니다. 보낸 쪽은 그걸 보고 "3번 편지는 안 왔구나"를 압니다. 그리고 명중 소식 같은 중요한 편지는 등기우편처럼, 출석부에 체크될 때까지 매번 다시 동봉합니다.

왜 이 방법인가

방법장점단점판단
받을 때마다 ACK 패킷 따로 전송단순패킷 수 2배, ACK도 잃어버릴 수 있음비효율
모든 패킷에 출석부 32비트를 덧붙임추가 패킷 0개, ACK 하나를 잃어도 다음 출석부가 다시 알려 줌패킷마다 6바이트(ack 2 + bits 4)이번 선택 (Gaffer On Games 방식)
재전송 타이머 (TCP 방식)대역폭 절약타이머를 기다리는 동안 멈춤1편 F2의 원인

모든 패킷에 최근 33개의 수신 여부를 덧붙이고, 중요한 이벤트는 확인될 때까지 계속 다시 싣는다.

11 · 2편에서 가장 어려운 부분

결정론: C++과 C#이 비트까지 같아야 하는 이유

예측과 재조정이 동작하려면 서버(C++)와 클라이언트(C#)의 이동 계산이 같은 입력에 대해 비트 하나까지 같은 결과를 내야 합니다. float 계산은 순서와 방식에 따라 마지막 자리가 달라지므로, 규칙을 정해 지켜야 합니다.

같은 레시피로 두 주방에서 빵 굽기입니다. 재료를 넣는 순서, 저울의 눈금, 오븐 온도를 똑같이 해야 같은 빵이 나옵니다. "대충 같은 순서"로는 안 됩니다. 반죽을 섞는 순서만 달라도(a+b)+c와 a+(b+c)처럼 결과가 미세하게 달라지기 때문입니다.

지킨 규칙 4가지

  1. 삼각함수 금지. sin, cos는 언어·기기마다 마지막 자리가 다를 수 있습니다. 그래서 방향은 클라이언트가 카메라 회전을 반영한 월드 방향(−127~127 정수)으로 보내고, Step() 안에서는 곱셈, 나눗셈, sqrt만 씁니다. sqrt는 IEEE 표준이 정확히 반올림하도록 정해 둔 연산이라 어디서나 같습니다.
  2. 타이머는 정수 틱. "0.1초"를 float로 빼 나가면 오차가 쌓입니다. 코요테 타임은 "3틱"입니다.
  3. 연산 순서를 줄 단위로 일치. C# Movement.cs와 C++ movement.h는 같은 줄에 같은 식이 있습니다.
  4. 상수는 반올림이 끝난 값을 적는다. 1/30은 0.0333333351F로 양쪽에 같은 숫자를 적었습니다.

검증

C++이 무작위 입력 3,000틱(공중 1,643틱, 구르기 198틱 포함)의 결과를 파일로 쓰고, C#이 같은 입력을 넣어 14개 필드를 비트 단위로 비교합니다. 재검증 후에도 3,000 / 3,000 일치입니다. 테스트 통과 이 검사를 CI에 넣어 두면, 누군가 한쪽만 고치는 순간 머지가 막힙니다.

서버와 클라이언트가 같은 레시피를 같은 순서로 따르도록 규칙을 정하고, 3,000틱 비교 테스트로 매번 확인한다.

12 · 재검증에서 추가 · 수정 이유

패킷 예산 1,200바이트와 "가까운 것부터"

UDP 패킷이 너무 크면 중간 경로에서 여러 조각으로 쪼개지고, 조각 하나만 잃어도 패킷 전체가 버려집니다. 그래서 스냅샷 하나를 1,200바이트 안에 맞추고, 넘치면 먼 엔티티부터 뺍니다.

단체 사진입니다. 사진 한 장(패킷)에 다 못 들어가면, 앞줄(가까운 사람)부터 찍고 뒷줄은 다음 장에 맡깁니다. 그리고 동료(다른 플레이어)는 거리와 상관없이 항상 사진에 넣습니다.

왜 이 방법인가

방법장점단점판단
전부 보내기 (재검증 전)단순몬스터 200마리면 약 2.2KB → 쪼개짐, 255개 넘으면 개수 필드가 넘침버그
가까운 순으로 예산까지코드 20줄, 크기 상한 보장먼 엔티티는 업데이트가 끊김이번 선택 (가장 단순한 관심 영역 관리)
우선순위 누적 + 델타 압축먼 것도 가끔씩은 갱신, 바뀐 것만 전송구현 복잡다음 단계 (2편 12장)

패킷 하나는 쪼개지지 않는 크기로 고정하고, 넘치면 중요한 것(동료, 가까운 적)부터 담는다.

13 · 서버 구조

스레드는 몇 개가 필요한가

프로토타입은 스레드 1개로 "받기 → 틱 → 보내기"를 모두 합니다. 방이 많아지면 받고 보내는 일과 게임 규칙을 돌리는 일을 다른 스레드로 나누고, 그 사이는 큐로 연결합니다.

식당입니다. 홀 직원(I/O 스레드)은 주문을 받아 주방 앞 주문표 꽂이(큐)에 꽂고, 완성된 음식을 손님에게 가져다줍니다. 요리사(로직 스레드)는 정해진 테이블만 맡아서 주문표를 꺼내 요리합니다. 한 테이블을 두 요리사가 동시에 만지지 않으니 서로 부딪힐(락) 일이 없습니다.

왜 프로토타입은 1개인가

멀티스레드는 빨라지는 대신 "두 스레드가 같은 데이터를 동시에 바꾸는" 버그(경쟁 상태)가 생길 수 있고, 이런 버그는 재현이 어렵습니다. 현업 원칙은 측정해서 필요해질 때 나눈다입니다. 나눌 때도 방 하나는 항상 같은 스레드가 맡게 해서, 게임 규칙 코드(World)는 지금처럼 락 없이 그대로 둡니다.

받고 보내는 일과 규칙을 돌리는 일을 큐로 나누고, 방 하나는 한 스레드만 만지게 해서 락을 없앤다.

14 · 클라이언트 쪽 개념 3가지 · 1편 F5, F8, F9

렌더 보간, 조합, 오브젝트 풀

클라이언트 쪽은 Unity 경험이 있으니 짧게 정리합니다. 셋 다 2편 코드에 반영되어 있습니다.

렌더 보간 · 플립북

시뮬레이션은 30Hz인데 화면은 120fps라면, 그림 4장 중 3장은 같은 위치입니다. 플립북의 그림 사이에 중간 그림을 그려 넣듯, 직전 틱과 이번 틱 사이를 경과 비율로 섞어 그립니다(GameClient의 alpha).

상속 대신 조합 · 레고

원본은 PlayerState → Dealer → MultiDealer로 기능을 위에 덧칠했습니다. 통짜 장난감은 팔 하나를 바꾸려면 전체를 새로 사야 합니다. 레고는 입력 블록, 이동 블록, 표시 블록을 끼웠다 뺐다 합니다. 원격 플레이어는 같은 몸에 "네트워크 입력 블록"만 끼우면 됩니다.

2편 7장 클래스 다이어그램 참고

오브젝트 풀 · 머그컵

화살마다 Instantiate/Destroy는 일회용 컵입니다. 쓰레기(GC)가 쌓이고 수거차가 오는 순간 게임이 멈칫합니다. 풀은 머그컵을 씻어 다시 쓰는 것입니다.

15재검증에서 고친 것과 이유

2편의 프로토타입을 저장소에 넣기 전에 현업 기준으로 다시 검사했습니다. 사용한 도구는 다음과 같고, 결과는 모두 0건 또는 통과입니다.

  • 컴파일러 경고를 오류로 취급 (-Wall -Wextra -Wpedantic -Wshadow -Werror): 경고 0
  • 정적 분석기 clang-tidy (버그 위험, 성능, 분석기 규칙): 경고 0
  • AddressSanitizer + UndefinedBehaviorSanitizer로 테스트와 서버 실제 구동: 보고 0
  • C++ 단위 테스트 20개(검사 48개), C# 테스트 16개, C++ ↔ C# 일치 검사 3,000틱: 모두 통과
  • Unity 스크립트: API 스텁으로 타입 검사 (경고를 오류로)

아래 항목을 펼치면 무엇이 문제였는지, 실제로 어떤 상황에서 터지는지, 어떻게 고쳤는지, 왜 그 방법인지, 어떻게 확인했는지가 나옵니다.
