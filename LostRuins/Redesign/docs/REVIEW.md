# 재검증 기록

2편 프로토타입을 저장소에 넣기 전에 현업 기준으로 다시 검사하고 고친 항목입니다. 같은 내용을 그림과 함께 보려면 [docs/guide.html](guide.html)의 15장을 여세요.

## 사용한 도구와 결과

| 도구 | 결과 |
|---|---|
| 컴파일러 경고 (-Wall -Wextra -Wpedantic -Wshadow -Werror) | 경고 0 |
| clang-tidy (bugprone, performance, clang-analyzer 등) | 경고 0 |
| AddressSanitizer + UndefinedBehaviorSanitizer | 보고 0 (단위 테스트 + 서버·봇 실제 구동) |
| C++ 단위 테스트 (CTest) | 20개, 검사 48개 통과 |
| C# 테스트 (mono) | 16개 통과 |
| C++ ↔ C# 이동 일치 검사 | 3,000 / 3,000틱 비트 일치 |
| Unity 스크립트 | API 스텁으로 타입 검사 (경고를 오류로) |

## 항목

### R1. 네트워크에서 받은 값을 검증 없이 enum으로 바꿈 (보안)

- **무엇이 문제였나**: 패킷 타입 바이트를 그대로 PacketType으로 변환했습니다. 정적 분석기가 "범위 밖 값을 enum으로 캐스팅"이라고 경고했습니다.
- **실제로 터지는 상황**: 누군가 타입 9인 패킷을 보내면 switch 어디에도 안 걸리고 이상한 경로로 흘러갈 수 있습니다. 서버는 인터넷의 아무나 패킷을 보낼 수 있는 곳입니다.
- **어떻게 고쳤나**: ReadHeader가 1~4가 아니면 실패로 표시하고, 입력 개수(최대 4), 이벤트 개수(최대 32), 엔티티 종류도 같은 방식으로 검사합니다. C#도 똑같이 바꿨습니다.
- **왜 이 방법인가**: "받은 값은 의심부터"는 서버 프로그래밍의 첫 규칙입니다. 암호화·체크섬은 그다음 단계이고, 범위 검사는 비용이 거의 0입니다.
- **확인**: Protocol_RejectsUnknownPacketType, Protocol_RejectsTooManyInputs, Protocol_RejectsTruncatedPacket (C++), robustness 2건 (C#)

### R2. 입력 값의 범위 정화 (보안)

- **무엇이 문제였나**: moveX는 −127~127로 약속했지만 int8의 −128도 들어올 수 있었습니다.
- **실제로 터지는 상황**: 정상 클라는 만들지 않는 값입니다. 이번 코드는 정규화 덕분에 속도 이득이 없지만, 규칙이 바뀌면 조작된 입력이 이득을 볼 수 있습니다.
- **어떻게 고쳤나**: 서버가 입력을 읽는 즉시 Sanitize()로 −127로 맞춥니다.
- **왜 이 방법인가**: 클라 검증은 조작된 클라에서 의미가 없으므로 서버에서 직접 확인합니다.
- **확인**: Protocol_SanitizesInput

### R3. 스냅샷이 UDP 안전 크기 1,200바이트를 넘을 수 있었음 (버그)

- **무엇이 문제였나**: 엔티티를 전부 실었습니다. 몬스터 200마리면 약 2.2KB이고, 255개를 넘으면 8비트 개수 필드가 넘쳐 패킷이 깨집니다.
- **실제로 터지는 상황**: 큰 UDP 패킷은 경로 중간에서 쪼개지고, 조각 하나만 잃어도 전체가 버려집니다. 몬스터를 늘리는 순간 손실률이 몇 배로 뜁니다.
- **어떻게 고쳤나**: BuildSnapshot이 예산을 비트로 계산하고, 동료를 먼저, 그다음 가까운 순으로 담습니다. 정렬 대신 nth_element로 필요한 개수만 고릅니다.
- **왜 이 방법인가**: 가장 단순한 관심 영역 관리입니다. 델타 압축·우선순위 누적은 효과가 더 크지만 코드가 몇 배입니다.
- **확인**: 몬스터 200마리 시나리오에서 최대 패킷 1,200B, 평균 1,195B (실측)

### R4. 엔티티 번호가 한 바퀴 돌면 몬스터 번호와 겹침 (버그)

- **무엇이 문제였나**: 플레이어·몬스터·화살이 번호 카운터 하나를 같이 썼습니다.
- **실제로 터지는 상황**: 화살 6만여 발(3명이 쏘면 약 3시간)이 지나면 번호가 0으로 돌아와 몬스터 #5와 화살 #5가 동시에 존재합니다. 클라는 몬스터를 화살 모양으로 그리게 됩니다.
- **어떻게 고쳤나**: 플레이어·몬스터는 1~1023 고정, 화살은 1024~65535 안에서만 순환합니다.
- **왜 이 방법인가**: 번호 재사용 목록(free list)보다 단순하고, 화살 수명(3초)이 짧아 같은 번호가 동시에 살아 있을 일이 없습니다.
- **확인**: World_DynamicIdsWrapInsideTheirRange

### R5. 입력 지터 버퍼 추가 (품질)

- **무엇이 문제였나**: 입력이 서버 틱보다 조금 늦게 오면 서버가 직전 입력을 반복했고, 그게 예측 보정의 거의 유일한 원인이었습니다.
- **실제로 터지는 상황**: 왕복 100ms·손실 2%에서 20초 동안 보정 3회. 화면에서는 0.3m 정도 미끄러짐으로 보입니다.
- **어떻게 고쳤나**: 서버가 처음에 입력을 (1 + 버퍼)개 모은 뒤 시작합니다. 기본 1틱.
- **왜 이 방법인가**: 버퍼 0은 지연이 최소지만 흔들리고, 2틱 이상은 지연이 커집니다. 1틱은 이 게임 장르에서 무난한 절충입니다(8장 표).
- **확인**: 보정 3 → 0 (왕복 100ms·손실 2%), 서버 확인 지연 +1틱 (실측). World_InputBufferDelaysFirstStep

### R6. 틱마다·패킷마다 메모리를 새로 할당 (성능)

- **무엇이 문제였나**: 서버는 틱마다 엔티티 벡터·이벤트 벡터·BitWriter를 새로 만들었고, C#은 패킷마다 byte[], Snapshot, List, BitConverter 배열을 만들었습니다.
- **실제로 터지는 상황**: 클라이언트 기준 초당 수십~수백 번의 할당이 쌓여 Unity GC가 주기적으로 프레임을 멈추게 합니다(1편 F9와 같은 문제).
- **어떻게 고쳤나**: 서버는 버퍼를 멤버로 두고 clear 후 재사용, C#은 BitWriter.Reset, ReadSnapshot(into), FloatBits(공용체)로 할당을 없앴습니다.
- **왜 이 방법인가**: "뜨거운 경로(매 틱 도는 코드)에서는 할당하지 않는다"는 게임 서버·클라 공통 원칙입니다.
- **확인**: C# BitWriter 재사용 테스트 통과. Unity Profiler의 GC Alloc 열로 0B 확인 필요 (추정)

### R7. Windows UDP 소켓의 연결 리셋 함정 (버그)

- **무엇이 문제였나**: Windows는 UDP로 보낸 상대가 꺼져 있으면, 그 다음 recvfrom을 WSAECONNRESET 오류로 실패시킵니다.
- **실제로 터지는 상황**: 플레이어 한 명이 강제 종료하면 서버의 수신 루프가 그 틱에서 멈춰, 남은 두 명의 입력 처리도 늦어집니다.
- **어떻게 고쳤나**: 서버(C++)는 SIO_UDP_CONNRESET을 끄고, 클라(C#)도 같은 옵션을 끕니다.
- **왜 이 방법인가**: Windows 게임 서버에서 흔한 실수이고, 옵션 한 줄로 해결됩니다.
- **확인**: Linux에서는 해당 없음. Windows 빌드에서 확인 필요 (추정)

### R8. 소켓 객체 복사 금지 (안전)

- **무엇이 문제였나**: UdpSocket에 소멸자는 있었지만 복사 규칙이 없었습니다.
- **실제로 터지는 상황**: 실수로 소켓을 복사하면 두 객체가 같은 핸들을 갖고, 하나가 닫힐 때 다른 쪽도 닫혀 "가끔 서버가 아무것도 못 받는" 버그가 됩니다.
- **어떻게 고쳤나**: 복사 생성·대입을 delete하고 이동만 허용했습니다 (C++ rule of five).
- **왜 이 방법인가**: 컴파일러가 실수를 막아 주므로 런타임 비용이 0입니다.
- **확인**: 복사하는 코드는 컴파일 오류

### R9. 응답 없는 연결의 이벤트가 무한히 쌓임 (안전)

- **무엇이 문제였나**: ACK가 오지 않으면 이벤트 큐가 계속 커졌습니다.
- **실제로 터지는 상황**: 클라에서 서버로 가는 방향만 끊긴 상태(받기는 되고 보내기가 안 됨)라면 5초 타임아웃에도 걸리지 않고 서버 메모리만 늘어납니다.
- **어떻게 고쳤나**: 미확인 이벤트가 512개를 넘으면 연결을 끊습니다.
- **왜 이 방법인가**: 상한 없는 큐는 서버에서 메모리 고갈의 흔한 원인입니다.
- **확인**: 코드 확인

### R10. 양자화 반올림 경계 오류 (버그)

- **무엇이 문제였나**: "0.5를 더하고 버림"으로 반올림했습니다. 분석기가 "부정확한 반올림"으로 경고했습니다.
- **실제로 터지는 상황**: 0.49999997에 0.5를 더하면 float 반올림 때문에 1.0이 되어, 0이어야 할 눈금이 1이 됩니다. 0.78cm 한 칸이지만 틀린 값입니다.
- **어떻게 고쳤나**: std::lround로 바꿨습니다. 인코딩은 서버만 하므로 C#과의 일치에는 영향이 없습니다.
- **왜 이 방법인가**: 표준 함수가 경계값을 정확히 처리합니다.
- **확인**: Protocol_SnapshotRoundTrip

### R11. float 비교 의도를 코드로 드러냄 (품질)

- **무엇이 문제였나**: 재조정 판단에 memcmp(메모리 통째 비교)를 썼습니다.
- **실제로 터지는 상황**: 동작은 맞지만, 구조체에 필드가 추가되며 빈 공간(패딩)이 생기면 쓰레기 값까지 비교해 늘 다르다고 나올 수 있습니다.
- **어떻게 고쳤나**: BitwiseEqual()이 필드마다 비트를 비교합니다. C#의 BitwiseEquals와 같은 규칙입니다.
- **왜 이 방법인가**: "비트까지 같아야 한다"는 의도가 함수 이름에 드러나고, 구조체가 바뀌어도 안전합니다.
- **확인**: Movement_IsDeterministic

### R12. ACK 비트필드의 시프트를 명시적으로 (품질)

- **무엇이 문제였나**: 분석기가 "음수만큼 시프트할 수 있음"이라고 경고했습니다. 실제로는 앞에서 걸러져 일어나지 않는 경로였습니다.
- **실제로 터지는 상황**: C++에서 음수·32 이상 시프트는 미정의 동작이라, 컴파일러 최적화에 따라 엉뚱한 값이 나올 수 있습니다.
- **어떻게 고쳤나**: 1~31, 32, 그 외를 나눠서 각각 명시했습니다. 동작은 같습니다.
- **왜 이 방법인가**: "일어나지 않는다"를 사람이 아니라 코드가 보장하게 했습니다.
- **확인**: Ack_TracksOutOfOrderAndWrap (C++), 같은 기대값으로 C#도 통과

### R13. Windows 서버 틱이 흔들리는 문제 (품질)

- **무엇이 문제였나**: Windows의 기본 Sleep 해상도는 15.6ms입니다.
- **실제로 터지는 상황**: 33ms 틱을 0.5ms씩 쉬며 기다리면 실제로는 15.6ms씩 쉬어서 틱 간격이 31~47ms로 흔들립니다.
- **어떻게 고쳤나**: main에서 timeBeginPeriod(1)로 1ms 해상도를 요청합니다. Winsock 초기화도 프로세스당 한 번으로 바꿨습니다.
- **왜 이 방법인가**: 게임 서버·클라 모두 쓰는 표준 처리입니다.
- **확인**: Windows 빌드에서 확인 필요 (추정)

### R14. 실행 인자 검증과 정상 종료 (안전)

- **무엇이 문제였나**: atoi로 인자를 읽어 잘못된 값(포트 99999, 문자)을 그대로 썼습니다.
- **실제로 터지는 상황**: 포트에 "abc"를 넣으면 0이 되어 운영체제가 아무 포트나 배정합니다. 클라는 접속할 포트를 모릅니다.
- **어떻게 고쳤나**: strtol로 읽고 범위를 검사해 틀리면 이유를 출력하고 종료합니다. SIGINT·SIGTERM으로 정상 종료하고 통계를 남깁니다.
- **왜 이 방법인가**: 배포 스크립트에서 설정 실수를 바로 알아차리게 합니다.
- **확인**: 코드 확인

### R15. Unity 인스펙터 연결 누락을 시작할 때 알림 (품질)

- **무엇이 문제였나**: GameClient의 [SerializeField] 참조가 비어 있으면 첫 프레임에 NullReferenceException이 났습니다.
- **실제로 터지는 상황**: 씬을 새로 만들다 하나를 빠뜨리면 원인과 거리가 먼 줄에서 에러가 납니다.
- **어떻게 고쳤나**: Awake에서 모두 검사하고, 빠졌으면 어떤 항목인지 로그를 남기고 컴포넌트를 끕니다.
- **왜 이 방법인가**: "빨리, 정확한 위치에서 실패하라"는 원칙입니다.
- **확인**: 스텁 타입 검사 (Unity 실행 필요)

### R16. 테스트·분석 도구를 저장소에 포함 (테스트)

- **무엇이 문제였나**: 처음 프로토타입에는 자동 테스트가 일치 검사 하나뿐이었습니다.
- **실제로 터지는 상황**: 누군가 규칙을 고쳤을 때 무엇이 깨졌는지 사람이 직접 돌려 봐야 알 수 있었습니다.
- **어떻게 고쳤나**: C++ 단위 테스트 20개(CTest), C# 테스트 16개, .clang-format, .clang-tidy, 새니타이저 빌드 옵션, GitHub Actions CI를 추가했습니다.
- **왜 이 방법인가**: 현업 면접에서 "테스트는 어떻게 했나요"는 거의 반드시 나오는 질문입니다. 테스트 이름이 곧 규칙 목록이 됩니다.
- **확인**: 전부 통과, 새니타이저 0건, clang-tidy 0건

### R17. 자잘한 정리 (패딩, 컴파일러 오탐) (품질)

- **무엇이 문제였나**: SkillDef 구조체에 8바이트 빈 공간이 있었고, GCC 13이 vector::resize에 잘못된 경고를 냈습니다.
- **실제로 터지는 상황**: 성능 영향은 거의 없지만, 경고를 오류로 취급하는 빌드에서는 빌드가 실패합니다.
- **어떻게 고쳤나**: 필드를 큰 순서로 재배치하고, resize 대신 push_back으로 바꿨습니다. 경고를 끄지 않고 원인을 피했습니다.
- **왜 이 방법인가**: 경고를 하나 끄기 시작하면 진짜 경고도 함께 묻힙니다.
- **확인**: 경고 0으로 빌드
