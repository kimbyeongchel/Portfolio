전사·궁수·창술사·힐러 네 직업의 코드를 어떻게 다시 짰는지 보여 줍니다. 원본이 실제로 하던 일과 그 안에서 찾은 버그를 먼저 확인하고, 재설계한 표와 코드, 그 동작을 고정한 테스트를 차례로 봅니다. 마지막 장에는 그동안 이야기한 고민들을 하나씩 정리해 답을 달았습니다.

00이렇게 읽으세요

가장 궁금한 것이 직업 코드라면 04장부터 보셔도 됩니다. 탭을 고르면 그 직업의 원본 동작, 원본에서 찾은 문제, 재설계한 표, 실제 코드, 그 동작을 지키는 테스트가 한 화면에 나옵니다. 03장의 타임라인은 그 표의 숫자가 화면에서 어떻게 보이는지 움직여 보여 줍니다.

모든 숫자에 출처를 붙였습니다. 실측은 이 분석 환경에서 프로토타입을 돌려 잰 값, 테스트 통과는 자동 테스트가 확인한 동작, 코드 확인은 원본 스크립트·프리팹에서 직접 읽은 값, 계산은 표의 숫자로 계산한 값, 시뮬레이션은 이 페이지 안에서 가정을 두고 돌린 값입니다. Unity 안에서 실행해 본 값은 없습니다.

원본 코드 인용은 본인이 작성한 스크립트(병철 폴더)에서만 했습니다. 팀원 코드는 인용하지 않았습니다.

01요약

가장 크게 바뀐 점은 직업이 클래스가 아니라 "표 한 줄"이 된 것입니다. 원본은 PlayerState를 상속한 직업 클래스 네 개가 각자 코루틴으로 스킬을 돌렸고, 멀티플레이를 위해 그 클래스를 다시 상속한 Multi* 네 개가 메서드를 통째로 복사했습니다. 재설계에서는 스킬이 하는 일을 다섯 가지 부품(근접 판정, 투사체, 지원, 이동 규칙, 패시브)으로 나누고, 직업은 그 부품을 어떤 숫자로 조합하는지만 적습니다.

두 번째는 "언제 휘두르나"와 "맞았나"를 나눈 것입니다. 선딜·판정·후딜·쿨타임·콤보·충전 같은 타이밍은 C++과 C#이 한 줄씩 같은 코드로 계산해서, 내 화면은 누르는 순간 반응하고(예측) 서버와 어긋나지 않습니다. 데미지·명중·회복·버프는 서버만 계산하고 결과를 이벤트로 보냅니다.

원본을 다시 읽다가 버그 여섯 개와 기획 확인이 필요한 값 네 개를 새로 찾았습니다. 멀티용 전사 프리팹의 패시브 수치가 0이라 멀티에서는 전사 패시브가 아무 효과가 없었고, 전사에게는 힐러 버프의 공격·방어 증가가 다음 프레임에 지워졌습니다. 04장의 직업별 탭에 근거 코드와 함께 정리했고, 재설계에서는 각각을 테스트로 고정했습니다.

02구조가 어떻게 바뀌나

왼쪽이 원본, 오른쪽이 재설계입니다. 원본은 기능을 상속으로 덧붙였기 때문에 직업 하나를 고치려면 직업 클래스, 그 직업의 Multi 클래스, 화살·창·마법 같은 보조 스크립트, 프리팹 수치를 함께 고쳐야 했습니다. 재설계에서 직업마다 다른 것은 표 두 줄(타이밍 표, 효과 표)과 연출 에셋 하나뿐입니다.

03스킬 한 번의 일생

스킬 하나는 네 구간을 지납니다. 선딜(누른 뒤 판정이 나오기 전), 판정(이 동안 맞을 수 있음), 후딜(다음 행동을 못 함), 캔슬 구간(후딜이지만 이동·구르기로 끊을 수 있음). 충전 스킬은 앞에 충전이 붙습니다. 격투 게임에서 "프레임 데이터"라고 부르는 바로 그 표입니다.

아래 세 줄은 같은 스킬을 세 곳에서 본 모습입니다. 내 화면은 누르는 순간 시작하고(예측), 서버는 입력이 도착한 뒤 같은 틱 수로 계산하고, 동료 화면은 서버 결과를 받아 100ms 늦게 그립니다. 데미지 숫자는 서버 판정이 돌아와야 뜨므로 내 화면에서는 휘두른 것보다 RTT만큼 늦게 보입니다.

원본은 판정 시점이 왜 흔들렸나

원본은 판정 시점을 애니메이션 진행률로 기다렸습니다. 매 프레임 timer += Time.deltaTime을 더하고 timer / anim.length가 impactStartTime을 넘는 프레임에 칼 콜라이더를 켰습니다. 그래서 판정이 나오는 순간이 프레임 길이에 따라 달라지고, 멀티에서는 세 사람의 컴퓨터가 각자 다른 순간에 판정했습니다.

재설계는 반대로 갑니다. 판정 틱은 표가 정하고(예: 전사 1타 = 누른 뒤 5틱째), 애니메이션 재생 속도를 그 틱에 맞춥니다. 판정은 서버 한 곳에서만 하므로 화면마다 다를 일이 없습니다.

오른쪽 그래프는 시뮬레이션입니다. 전사 1타(타격 지점 0.15, 클립 1초 가정)를 프레임 시간이 ±20% 흔들리고 3% 확률로 40ms 끊기는 상황에서 2,000번 돌렸습니다.

스킬 타이밍: 상태 하나가 bool 여러 개를 대신한다

원본의 isAttack, attackState, isCombo, comboCount, skillNum, 코루틴 안의 timer가 하던 일을 AbilityState의 slot·phase·tick·step이 대신합니다. 가능한 조합이 정해져 있어서 "공격 중이면서 구르는 중" 같은 말이 안 되는 상태가 생기지 않습니다.

이동: 스킬은 속도를 건드리지 않고 규칙만 넘긴다

궁수 조준 감속은 원본에서 Dealer.set_speed 오버라이드였고, 공격 중 정지는 직업마다 velocity = Vector3.zero를 직접 썼습니다. 재설계에서는 스킬이 MoveMods(잠금·감속·돌진)만 정하고, 실제 이동은 Step 한 곳에서만 일어납니다. 1편 F8에서 이야기한 "부모 Move의 일부만 쓰고 싶어서 복사한 문제"의 답이 이것입니다.

효과: 판정 창, 투사체, 지원

서버는 판정 구간의 매 틱마다 그 스킬의 효과 표를 읽습니다. 근접 판정은 정해진 틱 범위 동안 매 틱 검사하되 같은 대상은 한 번만 맞히고, 데미지는 대상마다·타마다 따로 굴립니다. 투사체와 지원 효과는 판정 첫 틱에 한 번 나갑니다.

수치: 빼서 되돌리지 않고 매번 다시 계산한다

원본 버프는 "8초 뒤에 0.1을 빼는" 방식이었습니다. 그 사이에 다른 코드가 수치를 다시 쓰면 기준이 틀어집니다. 재설계는 버프의 남은 틱만 저장하고, 공격력은 쓸 때마다 기본값 + 패시브 + 버프로 계산합니다. 피해를 받는 순서도 한 함수에 적었습니다.

06Unity 쪽에서 바뀌는 것

Unity 스크립트는 규칙을 계산하지 않습니다. 예측기가 만든 스킬 상태를 받아 애니메이션을 틀고, 서버 이벤트를 받아 숫자와 이펙트를 그립니다. 연출 데이터는 ClassVisuals 에셋에 따로 두어, 애니메이션을 바꿔도 규칙 코드는 그대로입니다.

리타이밍은 현업 액션 게임에서 흔히 쓰는 방법입니다. 클립의 타격 지점까지 걸리는 시간을 표의 선딜 시간으로 나눈 값으로 재생 속도를 맞추면, 칼이 닿는 그림이 정확히 판정 틱에 나옵니다. 예를 들어 0.9초짜리 전사 1타 클립의 타격 지점이 0.15라면 0.135초 ÷ 5틱(0.167초) = 0.81배속으로 재생합니다.

C#에서만 생기는 함정

AbilityState는 struct입니다. 쿨타임을 ushort[] 배열로 두면 struct를 복사해도 배열은 같은 것을 가리켜서, 예측 기록 256칸이 모두 같은 쿨타임을 공유하게 됩니다. 재조정이 조용히 틀리는 종류의 버그라서 쿨타임을 필드 다섯 개로 풀어 두었습니다.

07통신에서 바뀐 것

직업이 생기면서 패킷에 직업 번호, 스킬 코드, 내 스킬 상태, 새 이벤트 종류가 들어갔습니다. 엔티티 하나가 6비트 늘었지만 평균 스냅샷은 여전히 250바이트 안팎입니다.

08검증

테스트. 서버 단위 테스트가 20개에서 37개로 늘었습니다(검사 107개, 전부 통과 테스트 통과). 새 테스트 17개는 아래 목록과 같고, 이름이 곧 지켜야 하는 규칙입니다. AddressSanitizer·UBSan 빌드에서도 같은 결과입니다.

C++과 C#의 일치. 직업 네 개를 각각 3,000틱씩, 무작위 이동·점프·구르기·짧게 누르기·길게 누르기(충전)를 섞어 돌리고 이동 14개 + 스킬 15개 필드를 비트 단위로 비교했습니다. 12,000틱 모두 같았습니다 테스트 통과. 이 중 스킬 사용 중인 틱이 5,699개, 충전 중 877개, 콤보 2·3타 295개라서 실제로 스킬 경로를 지나갔습니다.

부하 테스트. 실제 UDP로 서버 1개와 봇 3명(직업 조합을 시나리오마다 바꿈)을 20초씩 돌렸습니다 실측. "예측 일치"는 내가 예측한 상태가 서버 결과와 비트까지 같았던 비율입니다.

측정하다 찾은 버그200마리 시나리오에서 4.3m 보정이 한 번 나왔습니다. 부활 직후 서버가 새 입력을 기다리지 않고 옛 입력을 부활 위치에 반복해서 생긴 일이었습니다.

순서는 이렇습니다. 서버가 플레이어를 부활시킨 다음 틱에 큐에 입력이 없으면, 마지막 입력을 다시 적용하면서 번호는 옛 번호 그대로 둡니다. 클라는 그 번호에 대해 저장해 둔 예측(죽어 있던 자리)과 서버 결과(부활 위치에서 한 걸음)를 비교하니 4m가 어긋난 것으로 셌습니다.

고친 방법은 두 가지입니다. 서버는 부활 직후에도 처음 접속할 때처럼 입력 버퍼가 다시 찰 때까지 기다리고, 클라는 되감을 때 그 번호의 기준값도 서버 값으로 덮어씁니다. 고친 뒤 같은 시나리오에서 보정은 0번입니다. 이 상황은 World_RespawnWaitsForFreshInputInsteadOfRepeating 테스트로 고정했습니다.

09고민 노트

그동안 이야기하면서 나온 고민을 하나씩 정리했습니다. 각 항목은 당시 고민 → 판정 → 현업 기준의 답 → 이 재설계에서 어디에 반영됐는가 순서입니다. 판정은 세 가지입니다. 맞음은 그 방향이 옳았다는 뜻, 절반은 문제를 정확히 봤지만 해법이 다른 곳에 있다는 뜻, 방향 수정은 현업에서는 다른 길로 푼다는 뜻입니다.

10남은 것과 한계

Unity에서 실행해 보지 않았습니다. Unity 스크립트는 실제 Unity API와 같은 시그니처로 만든 스텁에 대고 타입 검사만 통과시켰습니다. 애니메이터 파라미터(skillSpeed, charging)와 ClassVisuals 에셋은 Unity 프로젝트에서 만들어 연결해야 합니다.

프레임 값은 설계값입니다. 원본 에셋에는 비율만 있고 클립 길이가 없어서 모든 클립을 1초로 가정하고 틱으로 바꿨습니다. 실제 클립 길이를 읽어 표를 한 번 보정해야 합니다. 궁수는 원본에 AnimationState가 없어 전부 새로 정한 값입니다.

기획 확인이 필요한 값은 코드에 [원본 확인 필요]로 표시했습니다. 창술사 강화 공격이 일반 공격보다 약한 것(60 대 65), 전사 패시브 0.07과 0 중 어느 쪽이 의도였는지, 번개검을 무작위 대상에서 가장 가까운 대상으로 바꾼 것, 화상과 저주를 중첩 대신 갱신으로 바꾼 것입니다.

설계만 하고 구현하지 않은 것은 컷신 동기화(서버가 "틱 N에 시작" 이벤트를 보내고 각 클라가 같은 서버 틱에 재생), 발 IK, 몬스터의 다양한 패턴입니다.

이 코드는 제가 작성했습니다. 면접에서 설명하려면 직접 다시 짜 보는 과정이 필요합니다. 추천 순서는 abilities.h의 StepAbility를 보지 않고 다시 쓴 뒤 Ability_* 테스트 여섯 개를 통과시키고, 그다음 ApplyHit을 다시 쓰고 World_* 테스트를 통과시키는 것입니다. 테스트가 정답지 역할을 합니다.

LostRuins 기술 포스트모템 4편. 숫자는 이 분석 환경(Linux, GCC 13, Release)에서 잰 값이며 실제 인터넷과 Unity에서 잰 값이 아닙니다.
